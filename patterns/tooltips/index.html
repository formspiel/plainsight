Tooltips

A small floating box of text that appears near an element on hover or focus. Every chart on this site uses one — but a tooltip is a sighted-only convenience layer, never the only place a value lives. This page documents the pattern once; each chart page links back here instead of re-explaining it.

This is the first built Cross-Cutting Pattern page — a smaller template than a full chart page (see Stacked Bar Chart for that one), since a pattern here is documented once and referenced from wherever it applies, rather than repeated per chart.

What a tooltip is for (and isn't)

On this site, a tooltip only ever repeats information that's already available elsewhere — the hovered/focused element's own accessible name, or (for the chart toolbar's icon-only buttons) its aria-label. It never introduces new information that exists nowhere else. That's a deliberate constraint, not an accident: a screen reader user already gets the full value on focus, from the element itself, with no tooltip involved at all. If a tooltip carried unique information, hiding it from the accessibility tree (see below) would make that information invisible to AT users entirely.

Keyboard-triggerable

Every tooltip on this site shows on both hover and keyboard focus, not hover alone — a common shortcut is to wire only mouseover/mouseout, which leaves sighted keyboard users with no visual confirmation of what they've navigated to, even though a screen reader user gets the same information via the focused element's own name regardless. Implemented with paired listeners on the same delegated handler (focusin/focusout alongside mouseover/mouseout) — see wireTooltip in any chart's own script.js.

Role and accessible-tree treatment

Every tooltip element on this site is aria-hidden="true" and carries no ARIA role at all. That's the direct consequence of the constraint above: since its content always duplicates the trigger's own accessible name, exposing it a second time would be redundant at best and, for a screen reader user tabbing through a dense chart, actively noisy. This is different from the WAI-ARIA APG's own tooltip role, which exists for cases where the tooltip genuinely is the description (wired via aria-describedby) — not this site's case, where the description and the tooltip are the same text shown two ways to two different senses.

WCAG 1.4.13 Content on Hover or Focus

This success criterion applies to any content — tooltips included — that appears on hover or focus and requires three things: it must be dismissible without moving the pointer or focus (unless it's an input error, or it doesn't obscure or replace other content), it must be hoverable if pointer hover triggered it (the pointer can move onto the additional content itself without it disappearing), and it must be persistent until hover/focus moves away, is dismissed, or the information is no longer valid.

How this site's tooltips measure up against WCAG 1.4.13
Requirement This site's tooltips
Persistent Yes — stays visible for as long as hover or focus remains on the trigger, with no timeout.
Hoverable Not applicable in practice: the tooltip itself is pointer-events: none and contains only plain text, never a link or button a user would need to move the pointer onto. The criterion exists to protect interactive tooltip content from disappearing before it can be reached — there's nothing to reach here.
Dismissible An honest open gap, not a solved case. There's currently no way to dismiss a shown tooltip other than moving focus or the pointer away from its trigger — no Esc handler, unlike this site's popover-style disclosures (see details-dismiss.js). The likely applicable exception ("doesn't obscure or replace other content") is arguable, not clearly satisfied: the floating tooltip is positioned near its trigger and can visually overlap a neighboring bar or hotspot. Left here deliberately, flagged rather than silently assumed compliant — exactly the kind of nuance an auditor should be checking for, not something a reference site should paper over just because it built the demo.

Touch / mobile

A tap collapses hover and click into one ambiguous gesture, with no reliable "the user has moved on" signal — this broke differently depending on what the tooltip's trigger actually does on tap. Found and fixed on the Stacked Bar Chart's own toolbar: a plain toggle button left its tooltip stuck visible (nothing ever fires a "leave" event on touch), a button that opens a panel produced a visible flash (tooltip shows on focus, then the panel-open code hides it, both in the same tap), and a download link showed no tooltip at all (the page moves on before the focus-triggered tooltip has anything to render).

The fix applied everywhere on this site: suppress the toolbar's tooltip specifically under (hover: none), (pointer: coarse) — not tooltips generally. A chart's own data-point tooltip (shown when a hotspot is tapped) has no competing action to interfere with it — a hotspot's only job is to be focused — so it needs no such suppression and works on touch as-is. Scoped via one selector, .chart-toolbar .chart-tooltip, in chart.css, rather than a blanket rule against .chart-tooltip — the two cases genuinely don't share the same problem, only the same CSS class.

Where this shows up on the site

Two real, different tooltip instances exist today, sharing one mechanism (buildTooltip/wireTooltip in each chart's own script.js — hand-written per chart, not imported, per this project's stance on accessibility code, see CLAUDE.md):

  • The chart's own data-point tooltip — shown on hover/focus of any hotspot, clamped to stay within the visible scroll/viewport bounds rather than centered blindly (see any chart's buildTooltip). Works identically on touch.
  • The toolbar's tooltip — one shared instance for all three icon-only toolbar buttons (pattern toggle, keyboard shortcuts, CSV download), since their accessible names come from aria-label with no visible text otherwise. Suppressed on touch (see above).

See Stacked Bar Chart, Double Bar Graph, or Donut / Pie Chart for the actual code — this page documents the pattern, not a third copy of it.

Common failure patterns seen in audits

Seeded with well-known, representative failures to start this page — not yet a team-sourced catalog from real audits. Replace/extend as the team encounters real examples (see CLAUDE.md's sourcing note).

  • Hover-only, no keyboard trigger. The most common tooltip failure by far: wired to mouseenter/mouseleave alone, so a sighted keyboard user tabbing through gets no visual value at all, even when the underlying data is technically reachable by a screen reader via the element's own accessible name. (WCAG 2.1.1 Keyboard)
  • The tooltip is the ONLY place a value lives — no accessible name, no data table, nothing else exposes it. A screen reader user gets nothing; a sighted mouse user gets everything. This is the specific trap this site's own "duplicate, never originate" rule (see above) exists to avoid. (WCAG 1.1.1 Non-text Content, 4.1.2 Name, Role, Value)
  • Exposed to the accessibility tree AND duplicating the trigger's own name — e.g. a tooltip with role="tooltip" and no aria-hidden, read out in addition to the element's own accessible name. Not incorrect exactly, but redundant enough in a dense chart (30+ stops) to actively degrade the experience it's trying to help.
  • Left running unmodified on touch — see "Touch / mobile" above for the three distinct ways this broke on this site's own first pass, before the fix.
  • No dismiss mechanism other than moving away — this site's own current, honestly-flagged gap (see the WCAG 1.4.13 table above). Worth checking for specifically on any tooltip whose content could plausibly obscure something the user needs to see underneath it.
